# BLOCKS.md

Patterns for Gutenberg blocks generated by the wordpress-development skill. Targets the modern block API (block.json + `@wordpress/scripts`) on WordPress 6.7+.

## Source layout

```
src/blocks/
└── {block-slug}/
    ├── block.json       # metadata, attributes, supports, dependencies
    ├── index.js         # registers the block
    ├── edit.js          # editor component
    ├── save.js          # frontend markup (or 'null' for dynamic)
    ├── style.scss       # frontend + editor styles
    └── editor.scss      # editor-only styles
```

`@wordpress/scripts` compiles `src/blocks/{slug}/` into `build/blocks/{slug}/`. PHP reads `block.json` from `build/`.

## block.json

```json
{
  "$schema": "https://schemas.wp.org/trunk/block.json",
  "apiVersion": 3,
  "name": "acme-order-tracker/order-status",
  "version": "1.0.0",
  "title": "Order Status",
  "category": "widgets",
  "icon": "list-view",
  "description": "Shows the status of the current order.",
  "textdomain": "acme-order-tracker",
  "supports": {
    "html": false,
    "align": ["wide", "full"]
  },
  "attributes": {
    "orderId": { "type": "number", "default": 0 },
    "showHistory": { "type": "boolean", "default": false }
  },
  "editorScript": "file:./index.js",
  "style": "file:./style-index.css",
  "editorStyle": "file:./index.css"
}
```

The block name MUST be `{plugin-slug}/{block-slug}`. Both kebab-case. No exceptions.

## Block registration (PHP)

```php
namespace AcmeOrderTracker;

class Custom_Blocks {

    public function register(): void {
        add_action( 'init', [ $this, 'register_blocks' ] );
    }

    public function register_blocks(): void {
        $blocks_dir = ACME_ORDER_TRACKER_PATH . 'build/blocks/';

        foreach ( glob( $blocks_dir . '*', GLOB_ONLYDIR ) as $block_dir ) {
            register_block_type( $block_dir );
        }
    }
}
```

This auto-registers every block under `build/blocks/`. Add a new block to `src/blocks/`, rebuild, no PHP changes needed.

## Block category (optional)

```php
add_filter( 'block_categories_all', function ( array $categories ): array {
    return array_merge( $categories, [
        [
            'slug'  => 'acme-order-tracker',
            'title' => __( 'Order Tracker', 'acme-order-tracker' ),
        ],
    ] );
} );
```

Then set `"category": "acme-order-tracker"` in each block's `block.json`.

## edit.js — minimal template

```js
import { useBlockProps, InspectorControls } from '@wordpress/block-editor';
import { PanelBody, ToggleControl } from '@wordpress/components';
import { __ } from '@wordpress/i18n';

export default function Edit({ attributes, setAttributes }) {
    const { showHistory } = attributes;
    const blockProps = useBlockProps();

    return (
        <>
            <InspectorControls>
                <PanelBody title={__('Settings', 'acme-order-tracker')}>
                    <ToggleControl
                        label={__('Show history', 'acme-order-tracker')}
                        checked={showHistory}
                        onChange={(value) => setAttributes({ showHistory: value })}
                    />
                </PanelBody>
            </InspectorControls>

            <div {...blockProps}>
                {__('Order status preview', 'acme-order-tracker')}
            </div>
        </>
    );
}
```

## save.js — static vs. dynamic

**Static block** — markup serialized into post content:

```js
import { useBlockProps } from '@wordpress/block-editor';

export default function save({ attributes }) {
    const blockProps = useBlockProps.save();
    return <div {...blockProps}>{attributes.label}</div>;
}
```

**Dynamic block** — render via PHP at request time. Set `"render": "file:./render.php"` in `block.json` and:

```php
<?php
// build/blocks/order-status/render.php
$order_id = (int) ( $attributes['orderId'] ?? 0 );
if ( $order_id <= 0 ) {
    return;
}

$status = get_post_meta( $order_id, '_order_status', true );
?>
<div <?php echo get_block_wrapper_attributes(); ?>>
    <?php echo esc_html( $status ); ?>
</div>
```

Prefer dynamic blocks when the output depends on runtime data (user, current post, DB lookup). Static blocks are fine for purely presentational markup.

## Block markup MCP

When generating block markup by hand (especially for tests or migration), use the `wp-blockmarkup` MCP instead of writing the `<!-- wp:block /-->` comment syntax manually. It validates against the block's schema.

## Build commands

```bash
npm run build      # production build
npm run start      # watch mode for development
npm run packages-update  # bump @wordpress/* packages
```

`@wordpress/scripts` reads from `src/`, writes to `build/`. Don't commit `build/`.

## Patterns to avoid

- **Don't** use `<InnerBlocks />` without `allowedBlocks` and `template` — runaway nesting kills performance.
- **Don't** localize attribute values via `setAttributes` inside `useEffect` without dependency arrays — infinite render loops.
- **Don't** hand-roll React state. Use `useState`, `useReducer`, or block attributes.
- **Don't** import from `@wordpress/element` for hooks — use `react` directly via the bundler's externals.
- **Don't** ship a custom HTTP client. Use `@wordpress/api-fetch` — handles nonces, base URL, errors.

## Testing checklist

- [ ] Block appears in the inserter under the expected category.
- [ ] Attributes persist across reload of the editor.
- [ ] Frontend renders without console errors.
- [ ] Editor renders without console errors.
- [ ] `npm run build` produces output in `build/blocks/{slug}/`.
- [ ] PHP block registration runs on `init`, not earlier.
- [ ] `block.json` validates against the schema (`$schema` line is enough; the bundler checks it).
