# DATAFORM.md

Patterns for React-driven admin **settings pages** built on `@wordpress/dataviews`' `DataForm` component, generated by the `wordpress-scaffold` and `wordpress-feature` skills. Targets WordPress 6.7+ with `@wordpress/scripts`.

`DataForm` (and its sibling `DataViews` for list screens) is the direction WordPress core is taking for admin UI — it powers the new data-driven admin screens. Prefer it for **new** settings pages when the plugin already ships a JS build. It is **pre-1.0 and still stabilising**: pin the package version, import from the `/wp` subpath (below), and re-check the field/form API on every `@wordpress/*` bump. Record any API drift in the feature's `findings.md`.

## When to reach for DataForm vs the PHP Settings API

| Use DataForm when… | Stay on the PHP Settings API (SECURITY.md §4) when… |
|---|---|
| The plugin already has a `src/` JS build (`@wordpress/scripts`). | The plugin is PHP-only — don't add a build step for one form. |
| The settings UI is non-trivial (conditional fields, live preview, grouped sections). | A handful of fields render fine as a server-rendered nonce'd form. |
| You want the look/behaviour to match the modern WP admin. | You need the page to work with JS disabled. |

Both are valid. The choice is the scaffold's "Settings page?" step — ask which the user wants. The security floor is identical either way.

## Source layout

```
src/
└── settings/
    ├── index.js         # mounts the React app into the admin container
    ├── form.js          # fields[] + form{} config for DataForm
    └── style.scss       # optional admin styling
```

`@wordpress/scripts` compiles `src/settings/index.js` → `build/settings/index.js` and emits `index.asset.php` with the exact dependency array + version hash. **Always** enqueue using that asset file — never hand-maintain the `wp-dataviews`/`wp-api-fetch` dependency list.

## 1. Register one option, exposed to REST (PHP)

The kit convention is one option per plugin — an array. That maps cleanly onto a single `register_setting()` of `type => 'object'` with a REST schema. The schema **is** your server-side validation: declare every property, constrain with `enum`, and set `additionalProperties => false` so unknown keys are stripped.

```php
namespace AcmeOrderTracker;

class Settings {

    const OPTION = 'acme_order_tracker_options';

    public function register(): void {
        add_action( 'init', [ $this, 'register_setting' ] );      // init: registers for BOTH admin and REST
        add_action( 'admin_menu', [ $this, 'add_page' ] );
        add_action( 'admin_enqueue_scripts', [ $this, 'enqueue' ] );
    }

    public function register_setting(): void {
        register_setting(
            'options',
            self::OPTION,
            [
                'type'              => 'object',
                'default'           => [ 'message' => '', 'size' => 'medium', 'enabled' => false ],
                'show_in_rest'      => [
                    'schema' => [
                        'type'                 => 'object',
                        'properties'           => [
                            'message' => [ 'type' => 'string' ],
                            'size'    => [ 'type' => 'string', 'enum' => [ 'small', 'medium', 'large' ] ],
                            'enabled' => [ 'type' => 'boolean' ],
                        ],
                        'additionalProperties' => false,
                    ],
                ],
                'sanitize_callback' => [ $this, 'sanitize' ],     // defense in depth — see §4
            ]
        );
    }
}
```

This makes the option readable/writable at `GET|POST /wp/v2/settings`. **WordPress core gates that endpoint on the `manage_options` capability** — reads and writes both require it — so REST exposure does not widen access. (`manage_options` is in the constitution's strict capability allowlist.)

## 2. Admin page + enqueue (PHP)

```php
public function add_page(): void {
    add_options_page(
        __( 'Order Tracker', 'acme-order-tracker' ),
        __( 'Order Tracker', 'acme-order-tracker' ),
        'manage_options',                                    // capability gate on the screen itself
        'acme-order-tracker',
        [ $this, 'render' ]
    );
}

public function render(): void {
    if ( ! current_user_can( 'manage_options' ) ) {          // belt-and-suspenders before output
        wp_die( esc_html__( 'Insufficient permissions.', 'acme-order-tracker' ) );
    }
    echo '<div class="wrap"><div id="acme-order-tracker-settings"></div></div>';
}

public function enqueue( string $hook ): void {
    if ( 'settings_page_acme-order-tracker' !== $hook ) {    // only on our screen
        return;
    }
    $asset = include ACME_ORDER_TRACKER_PATH . 'build/settings/index.asset.php';
    wp_enqueue_script(
        'acme-order-tracker-settings',
        ACME_ORDER_TRACKER_URL . 'build/settings/index.js',
        $asset['dependencies'],                               // includes wp-dataviews, wp-api-fetch, …
        $asset['version'],
        true
    );
    wp_set_script_translations( 'acme-order-tracker-settings', 'acme-order-tracker' );
}
```

Because `wp-api-fetch` is in the dependency array, `@wordpress/api-fetch` is auto-configured in admin with the REST root URL and the nonce middleware — calls carry the `X-WP-Nonce` header automatically. No manual `wp_create_nonce`/`wp_localize_script` for the REST path.

## 3. The `DataForm` app (JS)

**Import from the `/wp` subpath.** Under `wp-scripts`, `import { DataForm } from '@wordpress/dataviews'` resolves wrong; `@wordpress/dataviews/wp` is the build-safe entry. This is the single most common DataForm setup mistake.

`src/settings/form.js` — the field + layout config:

```js
import { __ } from '@wordpress/i18n';

export const fields = [
    {
        id: 'message',
        label: __( 'Message', 'acme-order-tracker' ),
        type: 'text',
        Edit: 'textarea',                                   // optional control override
    },
    {
        id: 'size',
        label: __( 'Size', 'acme-order-tracker' ),
        type: 'text',
        elements: [                                          // renders a select
            { value: 'small',  label: __( 'Small',  'acme-order-tracker' ) },
            { value: 'medium', label: __( 'Medium', 'acme-order-tracker' ) },
            { value: 'large',  label: __( 'Large',  'acme-order-tracker' ) },
        ],
    },
    {
        id: 'enabled',
        label: __( 'Enabled', 'acme-order-tracker' ),
        type: 'boolean',
    },
];

// Layout types: 'regular' | 'panel' | 'card' | 'row'. Group with children[].
export const form = {
    fields: [
        {
            id: 'bar',
            label: __( 'Announcement bar', 'acme-order-tracker' ),
            children: [ 'message', 'size', 'enabled' ],
            layout: { type: 'card', withHeader: false },
        },
    ],
};
```

`src/settings/index.js` — mount, load, persist via `apiFetch` against `/wp/v2/settings`:

```js
import { createRoot, useState, useEffect } from '@wordpress/element';
import apiFetch from '@wordpress/api-fetch';
import { Button, Snackbar } from '@wordpress/components';
import { DataForm } from '@wordpress/dataviews/wp';
import { __ } from '@wordpress/i18n';
import { fields, form } from './form';

const OPTION = 'acme_order_tracker_options';

function SettingsApp() {
    const [ data, setData ] = useState( null );
    const [ saved, setSaved ] = useState( false );

    useEffect( () => {
        apiFetch( { path: '/wp/v2/settings' } )
            .then( ( settings ) => setData( settings[ OPTION ] ) );
    }, [] );

    if ( ! data ) {
        return null;
    }

    const save = () =>
        apiFetch( {
            path: '/wp/v2/settings',
            method: 'POST',
            data: { [ OPTION ]: data },
        } ).then( () => setSaved( true ) );

    return (
        <>
            <DataForm
                data={ data }
                fields={ fields }
                form={ form }
                onChange={ ( edits ) => setData( ( prev ) => ( { ...prev, ...edits } ) ) }
            />
            <Button variant="primary" onClick={ save }>
                { __( 'Save', 'acme-order-tracker' ) }
            </Button>
            { saved && <Snackbar onRemove={ () => setSaved( false ) }>{ __( 'Saved.', 'acme-order-tracker' ) }</Snackbar> }
        </>
    );
}

const container = document.getElementById( 'acme-order-tracker-settings' );
if ( container ) {
    createRoot( container ).render( <SettingsApp /> );
}
```

`onChange` receives a partial edits object (only the changed fields) — merge it into state, don't replace.

## 4. Security — the layer the upstream tutorial omits

The WordPress.org DataForm article shows the wiring but **no** capability, sanitization, or validation guidance. For this kit those are non-negotiable (SECURITY.md). The settings-page floor:

- **Capability gate twice** — on `add_options_page` (the menu/screen) *and* with an explicit `current_user_can( 'manage_options' )` in `render()`. Use only constants from the constitution's strict capability allowlist.
- **The REST schema is validation, not decoration.** Every property typed, choices constrained with `enum`, `additionalProperties => false`. The settings controller rejects values that violate it before they hit the DB.
- **Add a `sanitize_callback` anyway** — defense in depth, and it covers non-REST writes (`update_option` elsewhere, WP-CLI). Sanitize each field with a function from the constitution's strict sanitizer allowlist:

  ```php
  public function sanitize( $value ): array {
      $value = is_array( $value ) ? $value : [];
      return [
          'message' => sanitize_text_field( $value['message'] ?? '' ),
          'size'    => in_array( $value['size'] ?? '', [ 'small', 'medium', 'large' ], true ) ? $value['size'] : 'medium',
          'enabled' => ! empty( $value['enabled'] ),
      ];
  }
  ```

- **Nonce is automatic, not absent.** `apiFetch` sends `X-WP-Nonce` because `wp-api-fetch` was enqueued — but that only authenticates the request; the `manage_options` gate on `/wp/v2/settings` is what authorises it. Don't drop the capability check thinking the nonce covers you.
- **Escape on the way out, as always** — any settings value rendered back into PHP-generated HTML (e.g. a frontend banner) goes through `esc_html`/`esc_attr`/`esc_url` per SECURITY.md §3. Storing through a sanitizer is not a substitute for escaping at output.

## Patterns to avoid

- **Don't** `import { DataForm } from '@wordpress/dataviews'` under `wp-scripts` — use `@wordpress/dataviews/wp`.
- **Don't** hand-write the script dependency array — read `build/settings/index.asset.php`.
- **Don't** register the setting without `show_in_rest.schema` — the REST controller won't expose it, and you lose server-side validation.
- **Don't** skip `additionalProperties => false` — without it, clients can stuff arbitrary keys into your option.
- **Don't** replace state in `onChange` — it hands you partial edits; merge them.
- **Don't** treat the REST nonce as authorisation — keep the `manage_options` checks.
- **Don't** enqueue the bundle globally — gate on the page `$hook`.

## Testing checklist

- [ ] Settings page appears under **Settings** for a `manage_options` user, and 403s / is hidden for others.
- [ ] `GET /wp/v2/settings` returns the option with defaults on a fresh install.
- [ ] Saving persists; reloading the page shows the saved values.
- [ ] Posting an out-of-`enum` or wrong-typed value is rejected (schema validation).
- [ ] Posting an unregistered key does not persist (`additionalProperties => false`).
- [ ] `sanitize_callback` runs for a direct `update_option()` call too.
- [ ] `npm run build` emits `build/settings/index.js` + `index.asset.php`.
- [ ] No console errors; the bundle loads only on the settings screen.
